# scripts/cppp — the CPPP award pipeline

Offline, not in CI. Reads the 4.92 M-row CPPP award scrape (two Arrow IPC files, 3.45 GB,
HF `rumourscape/tenders`, CC-BY-4.0) with duckdb over memory-mapped pyarrow tables and writes
seven JSON files to `research/raw/cppp/` — the seventh, `security.json`, is the security-buyer slice
(see "The security slice" below), written by `security.py` inside the same run, which then writes
`security-page.json`, its winner-free projection for the page (see "The page's file" below). Quality first, then
rates. Every file carries a
`provenance` block: input digests (`sha256_16`), raw rows, distinct `tender_id`s, rows after
dedup, the dedup rule, the buyer rule, the marker regex, the value-band thresholds, the exact
SQL of every table (the module-level constants in `build.py`, verbatim), `generatedBy`
(`scripts/cppp/build.py@<git sha>`) and `asOf`. A reader can re-derive any number.

## Rebuild

```bash
pip install --user duckdb pyarrow          # Python 3.11; duckdb 1.5, pyarrow 25 were used
python3 scripts/cppp/build.py --arrow-dir <dir with data-0000*-of-00002.arrow> --out research/raw/cppp --as-of 2026-09-26
python3 -m unittest scripts/cppp/test_build.py   # 27 tests on a 2,940-row synthetic fixture, ~3 s
python3 -m unittest scripts/cppp/test_verify.py  # 28 tests: parser, guard, and the written sample's invariants
```

Every order-sensitive query carries a total ordering (a tiebreak column after each ranked value), and
`test_build.py` re-runs the build and asserts all seven files are byte-identical, so a re-run over the same
inputs reproduces every array byte for byte. `timing.json` counts rows with a NULL `aoc_at` or
`closing_at` (`excludedDateMissing`, 0 in this scrape) so that `n + excludedAocBeforeClosing +
excludedDateMissing` always equals the dedup row count.

The Arrow files are the HF `datasets` stream format (`pyarrow.ipc.open_stream`; the loader falls
back to `open_file`). Opening takes < 1 s; the digests ~11 s; the whole run about 2 minutes
(328 s on 2026-09-26; 318 s with the security slice on 2026-10-04, of which the slice is ~67 s). The fixture is regenerated by the tests from
`fixtures/make_fixture.py` (seed 2026); every value in it is invented, including every name.
`npm run test:cppp` is deliberately NOT wired: CI does not install duckdb/pyarrow and
`package.json` is unchanged.

## The dedup rule

> one row per (tender_id, selected_bidder_norm, aoc_at) — the first by internal_id

selected_bidder_norm = lower(trim(selected_bidder)); NULL bidders compare equal within a tender_id; internal_id is a 32-hex string so 'first' is lexicographic. The alternative rule 'one row per tender_id' is counted alongside so the reader sees the range; it is NOT applied because a tender with several lots awarded to different bidders is several award decisions.

On the real data the rule removes **1,536,727** of 4,921,960 rows, leaving
**3,385,233** award decisions. The alternative "one row per `tender_id`" would leave
2,923,713 (removing 1,998,247); a third reading, one per
(`tender_id`, bidder) ignoring the AOC date, leaves 3,298,256. The range
2,923,713–3,385,233 is the honest uncertainty about how many awards the scrape holds. The
one-per-`tender_id` reading is wrong for at least one visible reason: the heaviest "tender_id"s are
`2018_BHEL_EDN` (42,339 rows, 1,046 distinct bidders), `2017_BHEL_EDN`,
`2016_BHEL_EDN` … — year/organisation buckets, not tenders (`quality.json → duplicates.heaviestTenderIds`).

## What the other files hold

- `rates.json` — denominator **"awards after dedup with bids_received >= 1 and <= 1000"**
  (n = 3,019,420); single-bidder rate, mean and median bids with 95 % Wilson intervals by portal ×
  AOC year, normalised tender type ({Works, Goods, Services, Limited, Other/unknown}; the `Limited`
  class folds `LIMITED TENDER-SRM`, `Limited.`, `LT`, `Limited Tender(Mtrl)` … via the regex in
  provenance), value band (`<₹10 L`, `₹10 L–1 cr`, `₹1–10 cr`, `₹10–100 cr`, `>₹100 cr`, thresholds in
  `provenance.valueBandsInr`, plus one "value missing or implausible" row) and buyer. Buyers with
  n < 30 and the junk organisations are pooled under `pooled (n<30)`.
- `concentration.json` — per buyer with ≥ 50 awards with a named winner and a plausible value
  (1,215 buyers): HHI of award value and of award count among MARKED winners, top marked winner's
  share, the unmarked share as a number, and at most five marked winners with ≥ 5 awards for that
  buyer. Nobody else is named.
- `timing.json` — closing → AOC days histogram over 3,374,747 dedup rows (10,486 rows with AOC
  before closing excluded and counted); share ≤ 2 days = 2.04 %; AOC by month of the
  financial year (April = 1) and by portal.
- `redflags.json` — four Fazekas-style indicators, each as a rate over its declared family with the
  family size, a Wilson interval and an innocent reading: single bidding 11.22 % of
  3,019,420; `Limited` tender type 4.29 % of 2,729,190 (a floor: 15,755 rows carry
  Single/Nomination/STE-style labels that sit in Other/unknown); decisions ≤ 2 days 2.04 % of
  3,374,747; repeat single-bidder marked winners 51.28 % of 200,813 single-bidder
  awards to marked winners (7,777 of 74,940 buyer–winner pairs; pairs are counted, never
  listed). Plus the 25 public bodies with the highest single-bidder rate among buyers with ≥ 50 awards;
  a buyer is the body under the buyer rule, so '/'- and '||'-sub-units are folded into it (before the
  fold, 21 of the 25 were sub-units such as 'Bharat Petroleum Corporation Limited/RETAIL (LOG)' and
  '.../RETAIL (LOG)/RETAIL (LOG)-WR', listed separately, both at 100 %).
- `security.json` — the security-buyer slice: the same dedup rule and provenance block, over the award
  decisions whose buyer, department code or title names a security body, split into eight buyer classes,
  each rate beside the whole file. See "The security slice" below.
- `provenance.json` — the shared provenance block alone, and the list of the files this run wrote.
- `sample-verification.json` — written by `verify_sample.py`, not `build.py`: the 40-row live
  verification sample, its strata, RNG, marker and dedup rules, per-row fetch digests and field
  verdicts, and the finding (40/40 page_gone; see "Not a national statistic").

**Buyer rule.** central portal: the first '||' segment of organisation_name, then the first '/' segment of that, trimmed (the portal encodes organisation||department||division, and 772 organisations write the same hierarchy with '/' — 'Bharat Petroleum Corporation Limited/RETAIL (LOG)/RETAIL (LOG)-WR'; the first segment is the public body); state portal: organisation_name is the STATE, so the buyer is '<state> / <department code>' with the code parsed from tender_id (^\d{4}_([A-Za-z][A-Za-z0-9]*)_\d+_\d+$), or '<state> / unparsed' where the id carries no code
The central `organisation_name` has 10,402 distinct strings, 1,797 first '||' segments and 1,050 public
bodies once the '/' hierarchies are folded too (Bharat Petroleum Corporation Limited alone had been 23
"buyers", CE-MRRDA 11, BHEL 10, NALCO 6); the state portal has 34 states/UTs and 3,166 state/department buyers.

## The security slice (`security.json`)

`security.py`, called by `build.run()` after the red flags over the **same** duckdb connection, the same
`dedup` view and the same `provenance` block (plus `sliceRule` and `sliceSql`, the verbatim SQL of every
slice table). The rebuild command is unchanged. Every whole-file comparator in it is read from that run's
`rates.json` / `timing.json` / `redflags.json` values, not re-derived.

**What it is not** (its first field, `readMeFirst`, says so): defence capital acquisition is not on CPPP —
it runs through the Defence Procurement Portal under the Defence Acquisition Procedure; GeM purchases are
not here; most state police procurement is on the states' own portals. The slice is what the central armed
police forces, the services' headquarters, DRDO, BRO, MES, Defence Estates, the DPSUs and — where the
department code or the title says so — state police, prisons, fire and forensic bodies bought in the open
market and published on CPPP. Not a national statistic, for the reasons below.

**The rule** (every regex is printed in `sliceRule`):

- *central portal* — the lower-cased first `||` segment of `organisation_name` matches `centralBuyerRegex`
  (the union of the class members below plus `otherSecurityRegex`: defence, military, cantonment, NDRF,
  intelligence, police, home affairs/MHA, home department, forensic, fire service, home guard, civil defence,
  prison, jail, SPG, Cabinet Secretariat). A central row is in the slice by its **buyer**, not its purpose:
  CPWD building a CAPF barrack is not in it.
- *state portal* — the department code the buyer rule parses from `tender_id` matches
  `pol|jail|pris|fire|fsl|forens|igp|^dgp|^cid$|^hg|hg$|hga$|fes$|^fesa$` (route `department code`), less
  three keys whose own titles show they are not security bodies (`Maharashtra / DGPSP` government printing,
  `Andaman and Nicobar Island / DCFSL` forest works, `West Bengal / DMHG` district administration); **or** the
  title matches `stateTitleRegex` (route `title`). The bare title acronyms DGP, CID, FSL and bare "fire" are
  not used — in this scrape they are mostly reference-number tags, pipe fittings, water-tank levels and
  building fire-fighting installations — and the rows they would have added are counted
  (`quality.bareTitleTermsLeftOut`: 6,353 / 858 / 230 / 7,771 raw rows).
- junk organisations never enter.

**Buyer classes** — each central buyer key (the pipeline's buyer rule) takes the class of the first matching
member in `sliceRule.classMembers`, in order; `classes.map` lists every central key and every state key that
entered by its code, with its member and rows; `classes.memberCoverage` shows a member with 0 rows (HAL, BDL,
GRSE, BEML and the ED have no central buyer key of their own in this scrape) rather than dropping it.

| `works` | Military Engineer Services, Border Roads Organisation |
| `stores` | IHQ of MoD (Army) incl. OSCC, IHQ of MoD (Navy), Indian Air Force, Integrated Defence Staff, Coast Guard, Defence Estates |
| `research` | DRDO, Department of Defence Research and Development |

| `state-police` | every state-portal slice row, by route (`department code` / `title`) |

CSL is a Ministry of Ports, Shipping and Waterways company, classed `dpsu` because it builds for the Navy; a

MES alone is 74 % of the slice, so the slice total is a works rate; without `works` it is 12.20 %. Read by
class, never for the slice as a whole. `rates.byClassYear` puts each class-year beside the whole file for
the same AOC year and the same portal; `bands`, `timing` (the n-accounting identity of `timing.json`, per
class), `concentration` and `redflags` (the four indicators, by class, each beside its whole-file rate)
follow the sibling files' rules. Every table carries an `innocentReading`: works draw many bidders;
proprietary spares draw one; a DPSU buying from its own supply chain is not a market.

**Naming in the slice** is concentration.json's rule, unchanged: per buyer with ≥ 50 *marked* plausible
awards (concentration.json thresholds on all named awards; here on marked, so every HHI rests on ≥ 50 marked
awards), at most five marked winners with ≥ 5 awards for that buyer; per class, at most ten marked winners
by awards across the class, each with ≥ 5 awards from at least one buyer of the class. For a central buyer
the family is concentration.json's own, and counts, HHIs and names are identical there (value sums can
differ in the last paise: float sums in a different row order). Red flags count pairs, never list them.
`concentration.msOnlyNamed` counts the names admitted by "m/s" alone (16 of 255).

## The page's file (`security-page.json`)

`security_page.py` projects `security.json` into `security-page.json`. It carries what /security and
the /tenders security-buyers line read, plus the spec's SLICE list (`docs/design/SECURITY_PAGE.md`
§3.2, prerequisite S8). Those are `readMeFirst`, `classes.definitions`, `classes.map`, `headline`,
`quality.afterDedup`, `quality.total`, `quality.byClass`, `rates.total`, `rates.excludingWorks`,
`rates.byClass`, `rates.byClassYear`, `rates.innocentReading`, `caveat` and `provenance`. Each
subtree is verbatim and in the source's key order, written by the same `json.dumps` call as every
other file. Everything else is dropped. `dropped` lists each path with its reason. The two winner
lists (`concentration.byBuyer[].topMarkedWinners` and `concentration.byClass[].topMarkedWinners`)
read "names a winner; the page names none (spec C14)". `projectedFrom` gives the source file and
its `sha256_16`.

The guard collects every string held under a winner-list key in the source. It refuses to write if
any of them survives in the output, case-insensitively, inside any key or value. The error names
the path, never the string. There is one exemption. A DPSU that is a buyer in `classes.map` and
also a marked winner elsewhere (BEL today) keeps its map row as a buyer. Its string may be the whole
`classes.map[].buyer` value and nothing else.

`security.py` calls the projection after writing `security.json`, so every build refreshes it. On
its own it needs neither Arrow inputs nor duckdb:

```
python3 scripts/cppp/security_page.py                  # research/raw/cppp/security.json → security-page.json
python3 -m unittest scripts/cppp/test_security_page.py # stdlib only
```

On 2026-10-07 the projection took the file from 316,236 bytes to 170,174 bytes. `provenance`
(57 KB, with the verbatim SQL) is kept whole as the audit trail.

## The refusal

The scrape holds 2,386,037 rows whose winner is a bare personal name, or a comma-joined list holding
one — small contractors, private individuals with no public role, no CIN and no DIN; two people sharing a name cannot be told from
one person appearing twice (`scripts/prospect-procurement.mjs` states the same refusal for the two
state OCDS feeds; spec §1 non-goals). Therefore:

- No emitted JSON, this README, a log line or the test fixture names a winner unless the name matches
  the marker regex (case-insensitive): `ltd|limited|pvt|private|llp|m/s|infra|construct|enterprise|corporation|company|co\.|associates|traders|agencies|industries|technolog|solutions|services|builders|engineers|contractors|suppliers|&|and sons|society|samiti|sangh|mandal|federation|trust|bank|udyog|nigam|pariyojana`.
  Unmarked names are counted as "unmarked" and never written.
- **The component rule.** The portal lists several winners of one tender in one `selected_bidder`
  string separated by commas (1,205,994 of 4,540,739 named rows). A string is *marked* only when
  **every** non-empty `,`/`;`-separated component matches the regex; one firm in the list does not
  license the bare names beside it, and such a list is unmarked as a whole and never written
  (`build.py MARKED_SQL` / `is_marked()`, `verify_sample.py` the same; `provenance.markedRule`). The
  whole-string test used before 2026-09-26's second run had published 403 bare components inside
  477 joined names; it also inflated the marked share (59.18 % → see the table) and let HHI treat a
  joint list as one winner.
- In `concentration.json` a marked winner is named only with ≥ 5 awards for that buyer.
- `redflags.json` never lists winners at all; repeat pairs are counted.
- The bidder address column is never read. `test_build.py` proves both with sentinels in the fixture,
  which now carries comma-joined winners such as `Beta Constructions,ramesh kumar` at ≥ 5 awards for
  a heavy buyer: under the whole-string test they were named; the tests split every emitted name and
  assert every component matches.
- Buyers are public bodies and are named.
- Known soft spot: `m/s` (and `&`) are markers, so a sole proprietorship trading under a personal
  name — "M/s <first> <last>" — is admitted by the rule as specified. Of the 3,181 winners named in
  `concentration.json`, 243 are marked by `m/s` alone. Task 8's page may apply a stricter allow-list;
  the pipeline emits what the agreed regex admits and no more.

## Not a national statistic

No rate in these files is an Indian national statistic. The live verification sample
(`scripts/cppp/verify_sample.py` → `research/raw/cppp/sample-verification.json`; 40 marked-winner
awards, seed 2026, 20 central / 20 state over AOC years 2015–2026) was drawn and fetched on
2026-09-26. **All 40 pages were gone**: every stored `detail_url` answered HTTP 200 with the portal's
own "Invalid Url.Please Check" page. The link token is `<id>A13h1<key>A13h1<unix time>` and the time
segment is the June-2026 scrape timestamp, so the portal binds links to a validity window; a
headless-Chromium load gave the same page, the portal's Results-of-Tenders search sits behind an
image captcha and was not attempted, and no token was re-signed. Consequences:

- Not one field could be checked against the portal. `bids_received`, `selected_bidder`,
  `contract_value` and `aoc_at` remain **"reported"** (dataset-only) for every row; the row-level
  "documented" upgrade the plan allowed at ≥ 38/40 agreement is not available.
- The dataset's agreement with the live CPPP is **unknown** — not "good", not "bad".
- Every number here describes this scrape after the stated dedup rule, over the stated denominator,
  and nothing else. `rates.json → caveat` carries the same statement.

The sample file itself is a redraw: the first draw of 2026-09-26 tested the marker regex against the
whole `selected_bidder` string and admitted comma-joined lists carrying bare personal names; the
component rule (below) shrinks the candidate set, so with the same seed the 40 rows differ, and the
JSON says so (`redraw`). Both draws were 40/40 page_gone.
